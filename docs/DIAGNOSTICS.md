# Diagnostics

OmniDrop exposes one structured diagnostics snapshot through both:

```text
omnidrop-cli diagnostics
```

and **Help -> Copy diagnostics** in the desktop application.

The GUI collects worker information off the UI thread and copies the resulting JSON to the
clipboard.

## Schema version 1

A snapshot has four top-level groups:

```json
{
  "schema_version": 1,
  "app": {
    "name": "OmniDrop",
    "version": "0.1.0"
  },
  "runtime": {
    "qt_version": "...",
    "os": "...",
    "kernel_type": "...",
    "kernel_version": "...",
    "cpu_architecture": "...",
    "build_cpu_architecture": "...",
    "build_abi": "..."
  },
  "worker": {
    "ok": true,
    "capabilities": {
      "ok": true,
      "actions": ["file.sha256"]
    }
  }
}
```

When the local Python worker cannot start, the diagnostics command itself still succeeds and the
worker section records `ok=false` plus the startup error. This makes the diagnostics surface useful
for diagnosing missing Python/runtime configuration rather than failing for the same reason.

## Privacy boundary

The v1 snapshot intentionally does **not** include:

- Recent Files entries;
- Activity source paths;
- filenames currently selected in the GUI;
- file contents, hashes, extracted text, or action output;
- environment variables;
- tokens, credentials, or connected-account information;
- absolute application/user-data paths.

Worker capability output is generated by OmniDrop's own local worker and contains capability/runtime
status only.

Future diagnostics additions must preserve this redaction boundary or explicitly document any new
user-controlled data before it is included.
